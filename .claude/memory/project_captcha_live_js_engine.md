Built June 11 2026 to stop re-porting the captcha transform to PHP on every IVAC redeploy (they rotate the algorithm **version**, not just the seed). Now the **live bundle's own encrypt code is the source of truth** for both verification and (optionally) production encryption.

**Why:** each redeploy can change login/reserve to a different versioned encrypt module (10 ship in the bundle). A stale PHP port silently produces a 400. See [[kb_captcha_algorithm_verification]].

**How it works:**
- `app/Scripts/captcha_live_runtime.cjs` (+ `captcha_dom_stub.cjs`) — loads the cached bundle headless (DOM stub + neutered `setImmediate`/MessageChannel so React never renders; **wrapped in an IIFE** so a reload doesn't hit "Identifier '__mockEl' already declared"), auto-exposes every frozen `encryptText` module, runs the real one. One-shot CLI used by the analyzer.
- Monitor ground truth: `analyze_captcha_algo.py` extracts the version→module map (`wV={…,5:A0,6:J0}`) + `startAt:N,length:M,version:V` literals, runs the live module on the fixed test token, sets `impl_check.{login,reserve}` to **live** outputs. Hand-written `_REFERENCE_JS` was **deleted**. Also writes `storage/app/captcha/encrypt_meta.json`.
- `CaptchaAlgorithmService::analyze()` compares PHP vs live → `login_impl_match`/`reserve_impl_match` = "PHP matches live bundle"; caches `captcha:php_matches_live:{type}`; calls sidecar `/reload`.
- Sidecar `app/Scripts/captcha_encrypt_server.cjs` — systemd `ipms-captcha-encrypt` (`deploy/ipms-captcha-encrypt.service`, `127.0.0.1:8787`). Bundle loaded once (~1s); encrypt ~0.3ms. `/encrypt {type,token,secret,skip,encLen}`, `/health`, `/reload`; auto-reloads on file mtime.
- Engine `settings.captcha_engine` (default `php`) via `App\Services\Captcha\CaptchaEncryptionService` (`LiveBundleClient` = HTTP client), used by `CaptchaRequestController::show` + `CaptchaTokenController::storeSolved`: `php` | `live_js` (sidecar, falls back to PHP) | `auto` (PHP until monitor flags a type stale, then sidecar).
- Routes: `GET/POST /api/captcha-algorithm/engine`, `POST .../sidecar/reload`. UI: "Encryption Engine" panel on the monitor.

**How to apply (after IVAC redeploy):** run the monitor (refreshes bundle+meta, reloads sidecar). If PHP "DIFFERS from live bundle" for a type → switch engine to **Live JS** (zero PHP work) or re-port `CaptchaTokenTransformer.php`. Sidecar hot path stays fast; PHP is the default. `deploy/README-captcha-encrypt.md`.

**Historical gotcha (fixed by the Self-Healing upgrade below — was the bug that caused a live 400 on June 14 2026):** the monitor refreshing bundle+meta used to NOT be enough — the sidecar fed itself **secret/offset/length from the active `captcha_transform_seeds` row**, so you had to manually click **Apply Login/Reserve Seed** or it 400'd while reporting "healthy". This manual step is GONE now: meta carries the secret and the auto-refresh job auto-applies. Also fixed then: meta dropped `reserve` when the Python context-scan label was None → `_attribute_for_live()` elimination fallback so both types always land in `encrypt_meta.json`. See [[kb_captcha_algorithm_verification]].

**Sandbox note:** Claude Code's sandbox kills a process that loads the bundle AND binds a listener (signal 16) — can't run the sidecar via the Bash tool; systemd on the real host runs it fine. Verify the runtime with the one-shot CLI (no listener) instead.

## SELF-HEALING upgrade (June 14 2026) — bundle is the single source of truth, zero manual steps

Built so IVAC redeploys need no human action — the manual "Apply Seed" + "Run monitor" steps are gone. Three layers:
- **Bundle-as-truth:** `encrypt_meta.json` now carries the per-type **secret** too (`{module,version,skip,enc_len,secret}`), written by `analyze_captcha_algo.py::_compute_live_outputs` **atomically (temp+os.replace) and only when BOTH types fully resolve + both live runs succeed** (else last-known-good kept, `extraction_ok=false`). Sidecar `/encrypt` makes `secret/skip/encLen` **optional** → falls back to `state.meta[type]`; missing secret → 503. `LiveBundleClient::encrypt()` + `CaptchaEncryptionService` send NO secret/skip/encLen on the sidecar path (meta drives), so encryption is decoupled from the DB seed. `encrypt*()` now return `?string`; controllers treat a missing seed as non-fatal and only 500 when the encryptor returns null. DB seed is now just the PHP fallback + audit trail.
- **Auto-apply + auto-refresh:** `CaptchaAlgorithmService::analyze()` auto-calls `updateActiveSeed()` for both types on a clean extraction (gated: `extraction_ok` + no `extraction_alarm` + all detected values present) → `autoApplySeeds()`; on failure it keeps last-known-good and raises a **needs-attention** flag (`Cache::forever('captcha:needs_attention')`, also in `engineStatus()` + monitor banner). Command **`captcha-algorithm:auto-refresh`** (**NOTE Jun 16 2026: it is NOT scheduled — the `Schedule::command(...)->everyFiveMinutes()` line in `routes/console.php` is COMMENTED OUT "intentionally NOT scheduled". So there is NO cron auto-refresh; captcha encryption does NOT self-heal on redeploy — you must run the monitor "Run Analysis" or `php artisan captcha-algorithm:auto-refresh` by hand.** The root crontab DOES run `php artisan schedule:run` every minute, but this command isn't in the schedule. To enable auto-healing, uncomment that line.): cheap poll via `analyze_captcha_algo.py <proxy> --head-only` (HTML-only, returns Vite content-hashed `bundle_asset`) vs `Cache 'captcha:last_bundle_asset'`; unchanged→exit, changed→`analyze()` (re-extract+meta+auto-apply+sidecar reload), marker only advances on clean apply; skips during booking window.
- **Server-side proxy:** new nullable `settings.captcha_bd_proxy_url` (migration + `Setting` fillable), persisted by `CaptchaAlgorithmController::analyze` on each UI run, exposed via `engineStatus().bd_proxy_url`; the monitor Vue seeds its proxy from it when localStorage is empty. The command reads it.

**Recovery after redeploy is MANUAL** (the auto-refresh cron is disabled — see note above): run the monitor "Run Analysis" once (also persists the proxy), or `php artisan captcha-algorithm:auto-refresh`. After changing the sidecar `.cjs`, `systemctl restart ipms-captcha-encrypt` (a `/reload` only re-reads bundle+meta, not code).

**Eloquent gotcha fixed (`CaptchaTransformSeed::activate()`):** the old `static::where(type)->update(false); $this->update(true);` silently left ALL rows inactive when re-activating the **already-active** row — `$this->is_active` was already `1` in memory so `$this->update(['is_active'=>true])` was not dirty and issued no write, after the mass-update had set it false in DB. Auto-apply re-applies the active seed every clean run, so this bit immediately (command said "applied" but `active count=0`; `updated_at` advanced but `is_active=0` was the tell). Fix: both writes via query builder — `whereKeyNot($id)->update(false)` then `whereKey($id)->update(true)`. Regression test: `tests/Feature/Captcha/CaptchaTransformSeedActivateTest.php`. Watch for this pattern in any other `activate()`-style toggle.

Tests: `CaptchaEncryptionServiceTest` (added bundle-as-truth null-seed cases), `CaptchaAutoApplyTest` (clean→applies, unclean→needs-attention, via a `runScript()`-overriding subclass), `CaptchaTransformSeedActivateTest`. Verified end-to-end on the live host: meta-driven `/encrypt` (no secret sent) byte-correct for both types; `captcha-algorithm:auto-refresh` detects/no-ops correctly.

## Mid-rollout: config selects a version with NO module in the bundle (June 16 2026) — "Extraction Failed — Bundle Structure Changed"

Symptom: monitor "Run Analysis" reports `Extraction Failed — Bundle Structure Changed`, issues "Login: …ground-truth could not be computed (version-to-module dispatch…failed)" + "Login: no module is mapped in encrypt_meta". **Root cause was NOT our parser breaking.** Live bundle `mqg9wvds-UEx73nAt.js` set the **sign-in AND OTP** captcha config to `startAt:5,length:21,version:11`, but the bundle's dispatch table `yV={1:()=>Xe(()=>Promise.resolve().then(()=>UX)),…,10:…m4}` ships **only versions 1–10** → `yV[11]` is `undefined` → the shared captcha hook `CV(token,cfg)` does `const s=yV[a];if(!s)return` → returns `null` → IVAC's own sign-in submit (`disabled:!M`, body `{phone,password,c:M}`) is disabled. So **IVAC shipped an incomplete/mid-rollout bundle — the v11 login module isn't deployed yet**, not an algorithm rotation. Reserve was unchanged (`startAt:9,length:19,version:9` → module `J1`; same secret as the active seed) and resolved fine. There are 3 `CV` instances (sign-in `HV`, OTP `bU` both v11; reserve `TZ` v9); only `CV(G,TZ)` reserve is encrypted.

How to tell mid-rollout from a real break: dispatch table `yV` has 1–10 but a config's `version` exceeds it. Verify with: `grep -oE '[0-9]+:\(\)=>[A-Za-z_$][\w$]*\(\(\)=>Promise\.resolve\(\)\.then\(\(\)=>[A-Za-z_$][\w$]*\)\)' ivac-bundle.js` (module map) vs `grep -oE 'startAt:[0-9]+,length:[0-9]+,version:[0-9]+' ivac-bundle.js` (configs).

Fix shipped (this is diagnostic only — runtime already kept last-known-good safely): analyzer now returns `dispatch_versions` (`_compute_live_outputs`); `CaptchaAlgorithmService::detectExtractionAlarm` gets it and classifies a type whose `encrypt_meta[type].version` is absent from `dispatch_versions` (module null) as **severity `rollout`** (not `structural`) with a precise "IVAC mid-rollout, last-known-good retained, re-run later" message + `pending_rollout`/`unaffected` lists; the monitor Vue renders an **amber** banner for `severity==='rollout'` instead of the red "encryption may be broken" one. Test: `CaptchaAlgorithmGroundTruthTest` "classifies a not-yet-shipped captcha version as a mid-rollout". **No passthrough/guess was implemented** — the disabled-button evidence shows v11 is incomplete, not an intentional raw-token mode; correct action is wait for IVAC to ship the v11 module, then re-run the monitor.

UI follow-up: the monitor's per-type **Apply Seed** button shows whenever `*_seed_match===false` (detected secret differs from the active DB seed), which during a rollout invites clicking a seed that can't work (no module; sidecar ignores DB seed anyway; a PHP fallback would mix new secret + old algo = wrong token). Fixed: `resources/js/pages/CaptchaAlgorithm/Index.vue` `isPendingRollout(type)` = `results.extraction_alarm.pending_rollout.includes(type)`; for a pending type the Apply button is replaced with an amber "Awaiting IVAC rollout — keep last-known-good" note (both Login + Reserve panels). Normal (clean) runs still auto-apply via `autoApplySeeds()` + the 5-min `captcha-algorithm:auto-refresh` cron — the Apply button is only ever a manual fallback.

Caution learned: running `analyze_captcha_algo.py` directly (raw, not via the service) overwrites `storage/app/captcha/ivac-bundle.js` but does NOT reconcile — it desyncs the live bundle/meta pair (and writes root-owned files). ## Extraction hardening + regression corpus (June 16 2026)

Goal: make the *extraction* half (the brittle part — execution via `captcha_live_runtime.cjs` was already algorithm-agnostic) survive version rotations without reactive regex patching. The dispatch entry `CV(e,t)` is a **React component** (uses useRef/useState/useEffect + control-flow-obfuscated `n[yV(127,"OdxC")]` decoder indirection) so it CANNOT be called headless; and the config objects sit in lazy chunks with **no plaintext API-path strings** nearby — so "call the entry" and "API-path attribution" are both infeasible. What works instead (all shipped):
- **Version read off the LIVE config object**, not regex. The Node probe in `analyze_captcha_algo.py` now also captures `version:globalThis.{gv}.version` (it already read skip/enc_len off the object); `_compute_live_outputs` uses `site['version']` directly, dropping the collision-prone `_version_for((skip,enc_len)→regex-configs)` match. Robust to config-literal key reordering.
- **Marker-only attribution, NO heuristic guessing.** Corpus fact: **`dateLabel` sits next to the RESERVE config in 6/6 bundles** (the single reliable signal); `password` next to login in 4/6 (login falls to elimination). Removed the provably-wrong "larger enc_len = reserve" guess from BOTH `_attribute_for_live` (Python) and `CaptchaAlgorithmService::attributeCallSites` (PHP). Elimination is allowed ONLY when exactly one type is labelled and one group remains; if neither is labelled → both null → fail loud (needs-attention), never mis-attribute. (Trap case proving why: bundle `d8243809` has LOGIN = 9/19/v9 — the same triple that is RESERVE in four other bundles; enc_len/DB heuristics flip it, markers get it right.)
- **Canary** added in `_compute_live_outputs` + `detectExtractionAlarm`: (a) per-type **well-formedness** (`_wellformed_output`: output len==token len, untouched prefix[:skip]/suffix, transformed window all base64url) — catches anti-headless poisoning / wrong module / empty output; (b) **distinct modules** (login & reserve must differ unless versions equal). A clean extraction now requires module+secret+skip+enc_len **AND** wellformed **AND** distinct; else meta is NOT published (last-known-good kept) and the monitor alarms. New `analyze()` return keys: `wellformed`, `distinct_modules`.
- **Side-effect-free `--attribute <bundle>` CLI mode** (`attribute_only()`): resolves+attributes+runs live modules but writes NEITHER the bundle dump NOR encrypt_meta.json (`write_meta=False`). Returns `{login,reserve:{skip,enc_len,version,module,has_secret}, dispatch_versions, wellformed, distinct_modules, extraction_ok, pending_rollout}`.
- **Regression corpus test** `tests/Feature/Captcha/CaptchaAlgorithmCorpusTest.php` — shells `--attribute` over all 6 archived bundles in `storage/app/captcha/bundles/`, asserts exact login/reserve (skip,enc_len,version) + reserve-has-module + distinct + (for `9ccaa915` v11) login pending-rollout/no-module/not-clean. ~33s. ## Auto-refresh cron ENABLED + reconcile-downgrade design bug (June 21 2026)

- **`captcha-algorithm:auto-refresh` is now SCHEDULED** (`routes/console.php`): `->everyFiveMinutes()->withoutOverlapping()` (was commented out). Cheap `--head-only` probe each tick; full analyze only on asset change; **skips the booking window** (`window_start_time`..`window_end_time`). NOTE the live window was set wide (16:59:59–22:00:00), so the cron is blocked those 5h — it heals after 22:00. Root cron `schedule:run` drives it.
- **DESIGN BUG found (not yet fixed):** an UNCLEAN `analyze()`/Download (notice page, mid-rollout, transient bad fetch — anything where python returns non-error but extraction isn't clean) calls `registerBundleVersion(clean=false)` → `CaptchaBundleVersionService::reconcileActiveFiles()`, which mirrors `CaptchaBundleVersion::current()` (the DB **active row**) back onto `ivac-bundle.js`+`encrypt_meta.json` and reloads the sidecar. **If the true-live bundle was applied OUT-OF-BAND** (manual `--bundle`, or sidecar-only, with no `captcha_bundle_versions` row + no `activate()`), the DB active stays an OLDER bundle → an unclean Download **silently DOWNGRADES live encryption to that stale version**. This is exactly what bit June 21: live was on `21674522`/`mqnnw71d` (applied out-of-band last session, never registered), DB-active was the older `fb272f03`/`mqngme1y`; an unclean Download reconciled disk back to `fb272f03`. Durable fix options: (a) always `register()`+`activate()` the just-fetched bundle even on out-of-band/manual applies so DB-active == true-live; (b) make `reconcileActiveFiles()` refuse to restore an active row whose asset ≠ the just-fetched asset (a stale active is a downgrade, keep current on-disk last-known-good instead).
- **Marker-skip trap:** the redeploy marker `captcha:last_bundle_asset` is the cron's cheap change-detector. If disk reverts to bundle X but the marker still says Y, then IVAC serving Y again looks "unchanged" → cron SKIPS recovery forever. After any manual/forced disk state change, **clear the marker** (`Cache::forget(CaptchaAlgorithmService::BUNDLE_ASSET_CACHE_KEY)`) so the next reachable run re-analyzes.
- **Incident outcome (Jun 21 ~19:00):** user deleted the `21674522` archived bundle by mistake — it was NOT in git (only `bundles/<hash>.js` corpus dumps are, and 21674522 wasn't one) and the sidecar had already flushed it, so it is **unrecoverable locally**. IVAC was returning **403 on /signin** (CF/time-gate) so it couldn't be re-fetched. NOT an emergency: real booking race is ~window_start and was already over; live sat consistently on `fb272f03` (bundle+meta+sidecar all matched, just an older algorithm). Recovery = **click Download (or let the cron run) once IVAC stops 403ing** — a fresh fetch supersedes the deleted file; the specific bundle isn't needed. Marker was cleared + needs-attention raised so the monitor is honest and the next reachable run can't skip. **Corpus test `CaptchaAlgorithmCorpusTest` now references a missing `21674522` fixture → will fail until re-anchored to surviving bundles.** See [[feedback_captcha_storage_perms]] and [[kb_captcha_algorithm_verification]].

Alphabet chars still validated → still catches poisoned/wrong-module output. This is the durable correct invariant (real Turnstile tokens can carry `.`/`:` anywhere).

Any future canary/probe-output change MUST bump this.

### Analyzer FIXED for method-trapped configs (July 9 2026) — no more manual extraction

`analyze_captcha_algo.py` now extracts the `mrbvuy43`-generation bundles automatically (`--attribute` → both login/reserve `b$`/v2/skip1/enc27/Ah502, wellformed, `extraction_ok:true`; full `analyze` writes correct coherent meta). Two root causes were fixed:
- **Configs trapped in dead `static [computed](){…}` methods.** The old capture injected `globalThis.X=VAR` right after the config, but that line lives inside a method React never calls headless, so it never ran. Fix: `_enclosing_computed_method()` detects the enclosing computed-member method (`…[expr](){`); `_extract_method_decls()` pulls just its **top-level function decls + const/let/var decls** (helpers are hoisted, so order-independent); `_build_capture_patch` re-emits those at module scope (just inside the bundle's outer IIFE `}()`) followed by `globalThis.NAME=(SECRET_EXPR)`. This evaluates the secret expression directly against the decoder helpers — sidestepping the method's `this`-gated guards (`if(this[X]())return…` early-exits AND `if(this[Z]()){…config…}` gates, which no uniform stub `this` can satisfy) AND the obfuscated `startAt:_0x…("1")` props whose undeclared helper params throw. This is the same approach used to recover the secret by hand. Do NOT try to run the guarded method under a Proxy — the config is behind a truthy-gate while other guards early-return, an unsatisfiable combination.
  - Two subtle bugs fixed en route: (1) `_match_paren_back`/`_match_paren_fwd` must be **string-aware** — a guard `if(this[u(797,"O(8i")]()){` has a `(` INSIDE the string `"O(8i"` that a naive matcher miscounts, misreading the guard as a named function and aborting the walk. (2) `_extract_method_decls` must skip a control block by its **matching brace**, not to the next newline — helper decls often follow a guard block with no separator (`…}}function W(){…}`), so a newline skip swallows them (this dropped `function W`, used by the reserve secret).
- **Attribution when UI markers are 30–60 KB away.** These bundles moved the configs into shared chunks with no nearby `dateLabel`/`password` marker, so both configs come back `algorithm=None` → `_attribute_for_live` returned (None,None) → fail. Fix: an **identical-configs fallback** — when neither type is labelled BUT every secret-resolved site is byte-identical (same skip/enc_len/version AND secret), assign login/reserve from them (a mis-assignment between identical configs yields identical tokens, so it's provably safe). It deliberately does NOT fire when sites differ (still fails loud to avoid mis-encryption). For `mrbvuy43` login==reserve, so this is exactly right.

Verified: `--attribute` clean, full `analyze` writes correct meta + working encryption, `CaptchaAlgorithmCorpusTest` still passes (no regression on the 4 archived bundles), captcha suite 36 pass / 1 skip / 1 pre-existing unrelated failure (`GroundTruthTest` "enables disabled captcha providers" — mocked service, fails on the original analyzer too). Backup of the pre-fix analyzer in the session scratchpad (`analyze_captcha_algo.ORIGINAL.py`). Limitation: the identical-configs fallback only covers the case where login==reserve; a future redeploy with DIFFERING configs and absent markers would still need a real attribution signal (or the sidecar/manual path).

## `$`-prefixed module exposure bug (June 14 2026) — "Extraction Failed — Bundle Structure Changed"

Bundle `a778c048` rotated reserve to module **`$0`** (v7, skip4/enc29) and login to `g1` (v8, skip2/enc25). Analyzer reported `extraction_ok: False` / "Reserve ground-truth could not be computed". Root cause: `captcha_live_runtime.cjs` `MODULE_RE` started with a `\b` word boundary, which **never matches before a `$`-prefixed name** (both `$` and its preceding delimiter `,`/`;`/`=` are non-word chars → no boundary), so `$0` was silently not exposed (runtime had only 9 of 10 modules).
