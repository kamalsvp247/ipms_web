IVAC runs **two separate origin tiers**, both fronted by Cloudflare (discovered Jun 16 2026 via crt.sh + urlscan.io archive + direct cert/SNI probing):

**Website tier** (`ivacbd.com`, `www`, booking UI — a Laravel app):
- Origin = **78.128.60.143** (Telehouse, Bulgaria; PTR `cloud-9ec93e.managed-vps.net`, managed VPS), `server: Apache`, holds genuine `*.ivacbd.com` cert.
- `GET /` (correct SNI via `--resolve ivacbd.com:443:78.128.60.143`) → 200, `<title>Indian Visa Application Center</title>`, sets `XSRF-TOKEN` + `indian_visa_application_center_session` cookies (Laravel).
- This IS a real non-LB origin server, but it **404s the `/iams/api/v1/...` path** → useless to the bot.

**API tier** (`api.ivacbd.com` → `/iams/api/v1/...`, what the BOT hits):
- Origin = **AWS ALB in ap-south-1 (Mumbai)** — `server: awselb/2.0`. Stored bypass IPs `13.232.38.16` / `13.206.53.10` are ELB nodes (PTR `ec2-…ap-south-1.compute.amazonaws.com`).
- The API backend targets sit in **AWS private subnets** behind the ALB — **no public non-LB IP exists** for the API. The ELB node IPs are the deepest publicly-routable layer; "the main API server, not the LB" is not reachable by design.

**Consequence for the bot:** bypass IPs MUST be **live, healthy AWS ELB nodes**. A drained/decommissioned ELB node returns the LB's own `503 Service Temporarily Unavailable` (generic `awselb/2.0` HTML) — that means "target group has no healthy targets," NOT an app 503; no retry tuning fixes it. See [[project_bypass_ip_cleanup]]. Validate a bypass IP by requiring the **app's JSON** from `sign-in-v2`, not just a cert match (a drained node still serves the cert).

**Ruled out:** `13.205.58.240` (urlscan "appointment" assoc.) is AWS shared/telemetry (cert CN `prod2-1.telemetry.ap-south-1.poseidon.alameda.aws.dev`, Coral `UnknownOperationException`), not IVAC.

**UPDATE Jun 24 2026 — confirmed EKS topology + ALB IP recycling (api AND appointment):**
- API tier is **AWS-managed EKS** (NOT Rancher/self-managed). Proof: kube-apiserver is publicly exposed at **`13.232.38.16:443`** — cert `CN=kube-apiserver` / issuer `CN=kubernetes`, SANs leak cluster id **`9c154d7bd6ad328f86adececf4c87a12.gr7.ap-south-1.eks.amazonaws.com`**, node `ip-10-0-170-177.ap-south-1.compute.internal`, private IPs `10.100.0.1` (svc ClusterIP), `10.0.170.177` (node), `172.21.38.127` (pod). It 401s every path/Host with `{"kind":"Status",...}` + `audit-id` header (kube-apiserver doesn't vhost-route) — so `13.232.38.16` is the EKS **control-plane endpoint, NOT an app/ELB origin**; useless for bypass. Other ports (80/6443/8443/10250/NodePort 30000-32767) all CLOSED — no direct node/ingress exposure.
- Full path: **Cloudflare → AWS ALB (`server: awselb/2.0`) → EKS ingress → app pods** (private VPC `10.0.x`/`172.21.x`). There IS a load balancer.
- **ALB public IPs are SHARED & RECYCLED across AWS tenants** — `13.206.53.10` (a former IVAC bypass IP) now presents cert **`CN=*.nykaafashion.com`** (Nykaa Fashion) + `awselb/2.0` 503. This is WHY stored bypass IPs go stale: AWS reassigns ELB pool IPs to other customers within days. A brute scan mostly finds OTHER tenants' ALBs; only IPs whose cert is `*.ivacbd.com` AT scan-time count, and they rotate (hours-days).
- **`api.ivacbd.com` has NEVER had a public direct origin** — OTX passive DNS = Cloudflare-only since first record; CT logs = wildcard `*.ivacbd.com` only (no per-subdomain cert); no off-CF subdomain exists. There is **no stable origin IP to find**. The only durable handle is the ALB's own `*.elb.ap-south-1.amazonaws.com` DNS name, which is not publicly exposed (would need cluster creds — apiserver 401s all).
- **`appointment.ivacbd.com`** = presumed same shared cluster as api (corroborated, not proven — see Jul 1 2026 verification below), Cloudflare-fronted with a **managed challenge** (`cf-mitigated: challenge`, "Just a moment"). Bundle JS lives at `/assets/<hash>.js` referenced from `/signin`. **UPDATE Jun 25 2026 — the BD proxy is NOT actually required:** the CF challenge only gates HTML/non-static routes; `.js` assets are un-challenged on any CF edge IP, and `GET /.well-known/` leaks `index.html` (bundle name + version) challenge-free. Full proxy-free discover+download flow in [[kb_ivac_bundle_fetch]]. (Still no API origin IP for `api.ivacbd.com`.)
- **bypass_ips table is currently EMPTY** — bot reaches api.ivacbd.com THROUGH Cloudflare (CF bypass removed Apr 2026 per CLAUDE.md), so no stored origin pool is in use.
- **The 429s the bot hits are app-level, NOT Cloudflare/IP edge limits** — bodies are IVAC app JSON keyed to the account: `{"http_status":429,"message":"You can log in after 0 minute(s) and 25 second(s)"}` (login throttle), `{"message":"Please wait a little longer before trying again."}` (reserveSlot), `{"status":429,"channel":"spellbound","message":"...haven't uploaded a webfile..."}` (business-logic block). Finding an origin IP would NOT reduce these — they're per-user quotas. Real fix = parse the server-stated wait and back off exactly that long instead of the flat 20s `backoffSleep`. Scanner discriminator (`BypassIpScanner`): cert SAN contains `ivacbd` AND body is valid IVAC JSON.

**GET-probing `api.ivacbd.com` app endpoints (e.g. `/iams/api/v1/forgot-password/sendOtp`) — verified Jul 1 2026:**
- Plain `curl` (no browser TLS/JA3 fingerprint, no JS engine) → Cloudflare **403 managed-challenge page** (`cf-mitigated: challenge`), never reaches the Worker/origin.
- A real browser with a CF clearance cookie, OR Python **`cloudscraper`**, clears the Cloudflare challenge — **no BD proxy needed**; reproduced identically with and without the `bd-pr.oxylabs.io` proxy from [[reference_bd_proxy]]. That proxy is only load-bearing for the bundle-fetch/algorithm-monitor flow, not general CF-challenge clearance.
- Once past Cloudflare, a bare GET (no POST body, no Turnstile token) gets a **plain `503 Service Temporarily Unavailable`** with `Server-Timing: cfOrigin;dur=0,cfWorker;dur=~300-400ms` — a **Cloudflare Worker in front of the API rejects it before forwarding to the origin** (`cfOrigin;dur=0`). Deliberate reject of a malformed/method-mismatched request, not app-down and not an IP/geo block.
- Takeaway: real JSON from any `/iams/api/v1/...` endpoint requires an actual POST with the correct body shape + a valid Turnstile-derived token (`c` field) — GET-only probing (curl, browser nav, cloudscraper) always dead-ends at this Worker-level 403/503 regardless of proxy or client.

**POST-probing `sign-in-v2` with `cloudscraper` — verified Jul 1 2026, corrected finding:** even a real solved Turnstile token (user-supplied, transformed via the live `CaptchaEncryptionService::encryptLogin()` sidecar — genuine "1.…" token, correctly encrypted) plus correctly-shaped `{phone,email,password,c}` body STILL gets the identical Cloudflare-edge 503 (`cfOrigin;dur=0`, `Server: cloudflare`, CF beacon HTML). Ruled out: token validity is NOT what the edge is filtering on (a bad/dummy token gave the exact same rejection as a real one). Most likely cause: **`cloudscraper`'s TLS/JA3 fingerprint and HTTP/2 stack get filtered by a CF WAF/bot-management rule on this sensitive POST route**, distinct from the real bot's JDK HttpClient (HTTP/3-capable) traffic which the Worker evidently allows through to the origin in production. Conclusion: `cloudscraper` cannot be used to get a genuine backend response from `sign-in-v2` (or likely the other bot endpoints) — this class of probing is fingerprint-limited, not payload-limited. Don't burn further paid captcha solves testing this path with cloudscraper.

**`appointment.ivacbd.com` vs `api.ivacbd.com` — same-server verification, Jul 1 2026:** both share the identical Cloudflare Universal SSL cert (SHA1 `F8:73:E4:83:49:C8:F2:C5:81:20:D2:D4:E6:ED:9F:D3:AF:3F:D8:10`, serial `343F9D55DE9791F113CED33143AD2652`, `CN=ivacbd.com` wildcard) and identical anycast IP set — proves same Cloudflare zone/account only, NOT same backend (a zone wildcard cert covers every subdomain regardless of origin). **Ruled out the website-tier Bulgaria origin (78.128.60.143) for appointment**: `curl --resolve appointment.ivacbd.com:443:78.128.60.143` → Apache generic **403 Forbidden** (no vhost configured for this host, falls to catch-all), vs `--resolve api.ivacbd.com:443:78.128.60.143` → Apache **404 Not Found** (vhost matches, path missing) — confirms `appointment.ivacbd.com` is NOT hosted on the same Apache box as the main `ivacbd.com` website. Cannot go further: `api.ivacbd.com`'s own AWS ALB/EKS backend has no discoverable stable origin IP (see above), so there's no direct IP/cert to compare `appointment.ivacbd.com` against — same-cluster-as-api remains the best-supported hypothesis (same zone, both excluded from the Bulgaria origin, both Cloudflare-only) but is not conclusively proven at the infra level.
